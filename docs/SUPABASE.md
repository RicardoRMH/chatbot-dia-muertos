# Conectar el registro de interacciones con Supabase

El chatbot guarda cada interacción (pregunta, respuesta y fuentes) en la tabla
`interacciones` de Supabase. Sirve **solo para analizar después dónde falla el
buscador**: no entrena nada, no modifica el conocimiento y no altera la lógica del
chatbot. Si Supabase no está configurado o está caído, el chatbot responde igual.

---

## Requisitos

- Un proyecto en [supabase.com](https://supabase.com).
- La tabla `interacciones` creada, con RLS activado.
- Node.js 20 o superior y npm (para la versión local).

---

## Estructura de la tabla

Esta es la tabla que se debe crear. No se necesita ninguna otra:

```sql
CREATE TABLE interacciones (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    pregunta VARCHAR(3000) NOT NULL,
    respuesta VARCHAR(5000) NOT NULL,
    fuente VARCHAR(500),
    fecha_hora TIMESTAMPTZ DEFAULT NOW()
);

ALTER TABLE interacciones ENABLE ROW LEVEL SECURITY;
```

`id` y `fecha_hora` los genera PostgreSQL, así que la aplicación nunca los envía.

---

## Variables de entorno

El proyecto lee exactamente dos variables. Los valores van en `.env.local` o en el
panel de Vercel, nunca en el código.

| Variable | Para qué sirve |
| --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` | URL del proyecto. Identifica a qué base de datos se escriben las interacciones. |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` | Clave publicable (antes `anon`). Autoriza el `INSERT` junto con la política RLS. |

Dónde obtenerlas en el panel de Supabase: **Project Settings → API**.

- **Project URL** → valor de `NEXT_PUBLIC_SUPABASE_URL`
- **Publishable key** (en proyectos antiguos aparece como `anon` / `anon public`) →
  valor de `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY`

> **No uses la clave `service_role`.** Es secreta, tiene todos los permisos y no debe
> existir nunca en código que se ejecute en el navegador ni en una variable
> `NEXT_PUBLIC_*`. Aquí no hace falta: el registro es una simple inserción y RLS la
> autoriza. Si algún día hiciera falta una operación privilegiada, se usaría una
> variable sin prefijo `NEXT_PUBLIC_`, leída solo en el servidor.

## Configuración local

1. Copia el archivo de ejemplo, que ya está en el proyecto:

   ```bash
   cp .env.example .env.local
   ```

2. Rellena `.env.local` con tus valores:

   ```env
   NEXT_PUBLIC_SUPABASE_URL=TU_URL
   NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY=TU_CLAVE
   ```

3. Reinicia el servidor de desarrollo, porque las variables se leen al arrancar:

   ```bash
   npm run dev
   ```

`.env.local` está en `.gitignore` y **no debe subirse a GitHub**. El archivo
`.env.example` sí se versiona, pero sin valores, y sirve de plantilla.

---

## Configuración de Vercel

Para que la versión desplegada registre también:

1. En Vercel, abre el proyecto → **Settings → Environment Variables**.
2. Añade las dos variables de la tabla anterior para los entornos que uses
   (Production y Preview).
3. Guarda y **vuelve a desplegar**: los cambios de variables de entorno no se aplican
   a un despliegue ya hecho. Puedes forzar el redespliegue desde **Deployments** →
   el botón de reejecutar, o con un commit nuevo.

Las variables `NEXT_PUBLIC_*` se incorporan al bundle del navegador al compilar, por
lo que solo pueden contener valores públicos. Por eso la clave publicable es
adecuada y la `service_role` no lo sería.

## RLS

La tabla tiene RLS activado y **no debe desactivarse**. Con RLS activo y sin
políticas, nadie —tampoco la clave publicable— puede escribir, así que hace falta
una política que autorice únicamente el `INSERT`:

```sql
CREATE POLICY "permitir_registro_de_interacciones"
ON interacciones
FOR INSERT
TO anon
WITH CHECK (true);
```

Qué permite, en detalle:

- `FOR INSERT` — solo insertar. No autoriza `SELECT`, `UPDATE` ni `DELETE`.
- `TO anon` — únicamente al rol anónimo, que es el que usa la clave publicable desde
  el navegador. El rol `authenticated` no obtiene permisos.
- `WITH CHECK (true)` — la fila insertada debe cumplir las restricciones de la tabla
  (columnas `NOT NULL` y longitudes). No se filtran filas por contenido.

Con esta política el chatbot puede registrar interacciones y no puede leer la tabla.
Es lo contrario de abrir permisos: el registro es de solo ida.

**Comprobación de que RLS está bien puesto.** Con la clave publicable no se debe poder
leer nada. Esta consulta, por ejemplo, debe fallar con el error de permisos:

```bash
curl -s "$NEXT_PUBLIC_SUPABASE_URL/rest/v1/interacciones?select=*" \
  -H "apikey: $NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY"
```

Respuesta esperada: `{"code":"42501","message":"new row violates row-level security policy"}`
o `permission denied for table interacciones`.

**Alcance conocido.** La clave publicable viaja en el bundle del navegador, así que
cualquiera que abra la aplicación puede insertar filas directamente contra la API de
Supabase, sin pasar por el chatbot. Para una bitácora de análisis es un coste
aceptable; si en algún momento molestara, las opciones son poner un proxy en el
servidor con una clave del lado del servidor, o limitar el origen con una política más
estricta. No se ha hecho ninguna de las dos porque la primera añade una ruta de código
que el proyecto no tenía y la segunda impediría registrar interacciones reales.

## Prueba

1. Ejecuta el proyecto (`npm run dev`) y abre <http://localhost:3000>.
2. Escribe una pregunta, por ejemplo `¿Qué es el cempasúchil?`.
3. Espera a ver la respuesta y las fuentes.
4. En Supabase, abre **Table Editor → interacciones**.
5. Confirma que apareció una fila nueva con tu pregunta, la respuesta, las fuentes y la
   fecha. Repite con otra pregunta para ver cómo se acumulan.

Para revisarlas con detalle, en **SQL Editor**:

```sql
SELECT *
FROM interacciones
ORDER BY fecha_hora DESC;
```

Y un resumen de lo que más se pregunta:

```sql
SELECT
    left(pregunta, 60) AS pregunta,
    count(*)           AS veces,
    max(fecha_hora)    AS ultima
FROM interacciones
GROUP BY left(pregunta, 60)
ORDER BY veces DESC, ultima DESC
LIMIT 50;
```

Estas consultas se ejecutan desde el panel de Supabase, que corre como el rol
`postgres` y por eso puede leer la tabla aunque RLS no se lo permita al rol `anon`.
Esa es también la única forma de volver a leer lo registrado.

**Qué revisar en la tabla `respuesta`.** Si termina en `…[recortada]`, la respuesta
había superado los 5000 caracteres de su columna y se guardó incompleta, marcada a
propósito para que no pase desapercibida. Con la base actual el caso no ocurre: la
respuesta más larga ronda los 2600 caracteres. Del mismo modo, una `pregunta` acabada
en `…[recortada]` indica que el usuario pegó un texto de más de 3000 caracteres.

En la consola del navegador, si algo falla, aparece un aviso con prefijo
`[supabase]`. Si en vez de eso ves

```
[supabase] Interacciones no se registrarán: faltan NEXT_PUBLIC_SUPABASE_URL o NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY.
```

es que el `.env.local` no se está leyendo: revisa que exista en la raíz del proyecto y
reinicia `npm run dev`.

## Qué queda registrado y qué no

Se guarda una fila por cada turno de conversación con una pregunta:

| Columna | Contenido |
| --- | --- |
| `pregunta` | El texto que escribió el usuario, sin recortar. |
| `respuesta` | El texto exacto que se le mostró, ya con su línea de fuentes. |
| `fuente` | Los **identificadores** de las fuentes citadas, separados por `; `. |
| `fecha_hora` | La hora del registro, puesta por la base de datos. |

### Por qué `fuente` guarda identificadores y no nombres

La columna es `VARCHAR(500)`. La lista completa de instituciones con nombres largos
llega a **512 caracteres** en la entrada «Elementos de la ofrenda y su significado» y a
504 en «Exposición escolar sobre el Día de Muertos»: dos de las 50 entradas no
caberían y PostgreSQL rechazaría el `INSERT` (`value too long`), perdiendo esas
interacciones justo en las preguntas más ricas en fuentes, que son las que más
conviene analizar.

Guardar los identificadores (`cdmx-ofrendas; inpi-elementos-ofrenda; …`) ocupa 208
caracteres como máximo y evita el problema sin tocar el tipo de la columna. Cada
identificador es la clave con la que se relacionan en `data/fuentes.json` la
institución, el documento y la URL, así que al cruzar ambos conjuntos se recupera el
nombre completo de cada fuente.

```sql
-- Ejemplo: qué fuentes se citan más
SELECT fuente, count(*) AS veces
FROM interacciones
WHERE fuente IS NOT NULL
GROUP BY fuente
ORDER BY veces DESC;
```

Si prefieres guardar los nombres completos, la alternativa es ampliar la columna, y
eso sí es un cambio de esquema que hay que decidir a propósito:

```sql
ALTER TABLE interacciones ALTER COLUMN fuente TYPE VARCHAR(1000);
```

El código no necesita cambios en ese caso.

## Dónde está el código

| Archivo | Qué hace |
| --- | --- |
| `lib/supabase.ts` | Crea el cliente una sola vez a partir de las variables de entorno y expone `registrarInteraccion()`, que inserta la fila y nunca lanza un error. |
| `components/Chatbot.tsx` | Llama a `registrarInteraccion()` después de añadir la respuesta a la lista, sin esperar: la base no puede retrasar ni impedir la respuesta. |

`lib/supabase.ts` es el único punto que crea el cliente. Si algún día se cambia de
proveedor o de tabla, se toca ese archivo y el chatbot sigue igual.
